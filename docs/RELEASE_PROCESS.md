# Release Process

This document keeps Sèo Trum / Auto_social releases predictable for users, contributors, and open-source reviewers.

## Versioning

The project uses semantic versions:

- `MAJOR`: incompatible public behavior or deployment changes.
- `MINOR`: new user-facing capability that keeps existing workflows compatible.
- `PATCH`: bug fixes, documentation updates, small UI improvements, and security hardening.

The current version is stored in [`VERSION`](../VERSION).

## Release checklist

Before publishing a release:

1. Confirm the working tree contains no private runtime state:
   ```bash
   git status --short
   ```
2. Run the open-source checklist:
   ```bash
   cat docs/OPEN_SOURCE_CHECKLIST.md
   ```
3. Run tests relevant to the changed areas:
   ```bash
   make test
   ```
4. Build the Ops frontend:
   ```bash
   make build
   ```
5. Update:
   - `VERSION`
   - `CHANGELOG.md`
   - `README.md` or `README.en.md` if user-facing behavior changed
   - `NOTICE.md` if upstream attribution or bundled third-party material changed
6. Create a Git tag:
   ```bash
   git tag -a v$(cat VERSION) -m "Release v$(cat VERSION)"
   ```
7. Push the tag and create a GitHub Release with the CHANGELOG summary.

## Release artifacts

Preferred artifacts:

- Git tag generated by GitHub.
- Source archive generated by GitHub Releases.
- Docker image generated by `.github/workflows/docker-publish.yml`.

Avoid attaching ad-hoc `.zip`, `.rar`, or local build folders to releases.

## What must not be released

Do not include:

- `.env`
- page tokens or provider API keys
- `settings.json`
- `server/.secret_key`
- `server/.hub_token`
- SQLite databases
- customer conversations, phone numbers, or real CRM exports
- local demo archives such as `demo_pack.tar.gz`

## Hotfixes

For urgent fixes:

1. Branch from the latest release tag.
2. Apply the smallest safe patch.
3. Run targeted tests plus `make build` if frontend changed.
4. Release as a PATCH version.
